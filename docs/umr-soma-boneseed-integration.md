# UMR Studio's BONES-SEED SOMA Flip and the native SOMA route

Investigated 2026-11-02. This traces published code and data, not an executed Studio retarget. The native checkout is UMR `d1cdaedaf67a827198da71c5fa831f48b2e51f91`; the public `main` branch was at that revision, while Studio's separate `gh-pages` branch was at `b9d749900805fad4700df7ba9e229d57961be560`. The browser site describes a complete CPU-adapted pipeline and explicitly warns that its performance is not representative of native UMR. [Studio](https://hanyang9.github.io/UMR/umr_studio.html), [repository](https://github.com/hanyang9/UMR/tree/d1cdaedaf67a827198da71c5fa831f48b2e51f91), [published site revision](https://github.com/hanyang9/UMR/tree/b9d749900805fad4700df7ba9e229d57961be560).

## Selection and source identity

The [reference catalog](https://github.com/hanyang9/UMR/blob/b9d749900805fad4700df7ba9e229d57961be560/static/assets/reference_motions/catalog.json) identifies `boneseed_soma_flip` as “Bones-Seed SOMA — Flip”. The reference scene builds the cards from the catalog. Selecting a card loads its preview, not the solver pack: a live UI inspection confirmed the heading, 190 frames, 30 FPS and requests for the preview's motion, vertices, indices and root positions, without a source-manifest request. [Reference scene](https://github.com/hanyang9/UMR/blob/b9d749900805fad4700df7ba9e229d57961be560/static/js/reference-motion-scene.js).

The separate [preview manifest](https://github.com/hanyang9/UMR/blob/b9d749900805fad4700df7ba9e229d57961be560/static/assets/reference_motions/boneseed_soma_flip/manifest.json) records `motions_uniform/bvh/flip_090_002__A304_M.bvh`, SHA-256 `82972d8d9c0874325d4da19e6e56370a37176aac94eb4297983ad5e602aa641a`, source FPS 120.0048, stride 4 and 190 source frame IDs 0, 4, …, 756. Its playback FPS is 30; it stores 4,505 quantized preview vertices and 27,018 triangle indices. A preview is not the full solver mesh.

Starting browser retargeting passes the active ID to `BrowserUMRRuntimeExact.run`; *then* `loadExactSourcePack` downloads the manifest and arrays. The solver pack's frame IDs also decode to 0, 4, …, 756. It contains 18,056 vertices per frame, 36,108 faces, 4,096 source samples and their face IDs, template vertices, geodesic graph and sort order, face labels, root positions and wxyz orientations. The motion array is normalized float32 geometry; its shape is `(190, 18056, 3)`. Its [manifest](https://github.com/hanyang9/UMR/blob/b9d749900805fad4700df7ba9e229d57961be560/static/assets/browser_runtime/source/boneseed_soma_flip/source-manifest.json) gives height 1.771972775 m, source ground mode `none`, no interaction objects, and `pipeline: soma`. The loader checks array dtype/shape and caches by ID; its code does not check the declared SHA-256. [Viewer run call](https://github.com/hanyang9/UMR/blob/b9d749900805fad4700df7ba9e229d57961be560/static/js/mujoco-viewer.js), [source loader](https://github.com/hanyang9/UMR/blob/b9d749900805fad4700df7ba9e229d57961be560/static/js/umr-exact-source-pack-v1.js).

## What is computed for the current robot

1. The active robot T-pose is applied. The browser extracts its visual mesh with its configured point-cloud center and measures its height. It shifts the stored source template and points along the source bounding-box axis to the selected center ratio. It samples 4,096 robot exterior points using first-hit filtering, seed 9000, 8× oversampling and the manifest's visibility settings. The source samples and geodesic graph are supplied in the pack; they are not newly sampled at this point.
2. CPU/WASM correspondence training uses the source and current robot points and geometry, independently height-normalized, plus the source k=32 geodesic graph. The active [training contract](https://github.com/hanyang9/UMR/blob/b9d749900805fad4700df7ba9e229d57961be560/static/js/umr-exact-training-kernels-v1.js) runs **60 epochs**. Although the source manifest says 100, the runtime calls the fixed 60-epoch contract and cosine schedule; the manifest value does not control this loop. The resulting paired 4,096 source/robot slots are specific to this training run. [Runtime](https://github.com/hanyang9/UMR/blob/b9d749900805fad4700df7ba9e229d57961be560/static/js/browser-umr-runtime-exact-v1.js), [training loop](https://github.com/hanyang9/UMR/blob/b9d749900805fad4700df7ba9e229d57961be560/static/js/umr-exact-correspondence-wasm-v1.js).
3. Robot slots are projected to the current robot visual surface and bound to its rigid geometry. On the human side, learned slots are bound to the SOMA retarget template by closest face and barycentric coordinates; Flip takes the default direct path. Those same faces and weights reconstruct slot positions on every moving mesh frame. Triangle bases transport normals. Face part IDs classify the bound source slots; upper arms are split geometrically, then a deterministic seed-0 selection applies the manifest's 19 segment budgets and point/normal costs. Robot geometry ownership and human semantic label are different concepts. [Current-run pack construction](https://github.com/hanyang9/UMR/blob/b9d749900805fad4700df7ba9e229d57961be560/static/js/umr-exact-current-run-pack-v1.js), [robot binding](https://github.com/hanyang9/UMR/blob/b9d749900805fad4700df7ba9e229d57961be560/static/js/umr-exact-robot-binding-v1.js).
4. The moving, normalized surface is scaled by the current robot height for the solve; root positions are treated likewise. Source ground alignment is `none`. Ground maps and self-contact maps are constructed from the newly bound surface, rather than supplied as hand-authored contact labels. Manifest settings include 0.1 m ground and self-contact thresholds, 0.005 m ground snap, 128 ground points, 256 self-contact pairs, and a hard all-surface-slot ground constraint. Thresholds are normalized by robot height. Flip has no object contact. The browser uses MuJoCo Jacobians and Clarabel, with forward and backward trajectory passes, dynamic-programming selection, and LQR filtering under the manifest's settings. These are code/manifest observations, not verified numerical parity with native. [Browser solver](https://github.com/hanyang9/UMR/blob/b9d749900805fad4700df7ba9e229d57961be560/static/js/browser-umr-solver-exact-v1.js).

The browser's exact source pack stores the data necessary to drive this computation, but its manifest does not document the geometry generator, fitted shape input or exporter revision. The current public `gh-pages` recursive tree has the assets and runtime but no identifiable source-pack exporter; the manifest's available path history starts with site publication commit `6753a7ea5b987269542901d6ebf11b349824e068`. The preview identifies the clip, but does not prove which fit produced the solver geometry. The previously observed affine vertex comparison to local templates is a diagnostic, not provenance. The manifest's face labels also do not identify their generating correspondence. No claim of identical surface, model configuration, slots or solve results follows merely from matching motion family or topology.

## Native SOMA and the local jump-and-land

The pinned [BONES-SEED adapter guide](../externals/UMR/sample_data/bones-seed/README.md) specifies a shared uniform fit, actor-specific proportional fits, separate NVIDIA SOMA-X runtime assets and disabled SOMA pose correctives. Its example defaults name the same uniform flip file as the preview. In the native loader, the literal `motions_uniform` ancestor plus discoverable shape parameters selects `soma_bvh_boneseed_uniform` and the distinct `soma_uniform` template; a plain `raw/uniform` directory is not recognized. If the single-motion loader does not find a shape, it silently uses generic `soma_bvh`. The fitted path calls SOMALayer with BVH poses and the fitted identity; the generic path skins its neutral bind template with BVH global transforms. Both are SOMA surfaces driven by the BVH, not a conversion of motion to SMPL-X. [Loader](../externals/UMR/scripts/soma_source.py).

Native SOMA semantic labels can be transferred from SMPL-X segments using the SMPLX–SOMA mesh correspondence, with face majority and the upper-arm split. This is a surface-label correspondence, not evidence that the input motion is SMPL-X. A nearest-joint fallback exists; the local generic run used the correspondence path. [Native segment code](../externals/UMR/scripts/retarget_body_segment_surface.py). Studio's published face labels are compatible in role but their derivation is not established by their manifest.

Our [existing generic control](../experiments/umr-baseline-g1-somax-20261102/README.md) used the selected `jump_and_land_light_001__A001.bvh` with all 1,165 frames at native 120.0048 FPS, cm BVH translations and degree Euler channels, source Y-up mapped `[z,x,y]` into robot Z-up, zeroed fingers and ground alignment `none`. It generated fresh 4,096-point correspondence with 500 training epochs and used sequential warm start plus LQR, not the browser's 60-epoch and bidirectional/DP configuration. Its generic neutral surface is not the fitted uniform body. The local shared fit SHA-256 `61f0b96c8386a19d44823faf4399816642b7e20691ed5b398c7402921090096e` is byte-identical to NVIDIA Kimodo's published shared BONES-SEED fit; a fitted static CPU load succeeded, but this is not a fitted motion or retarget validation. [Evidence](../experiments/umr-baseline-g1-somax-20261102/records/uniform-fit-investigation.json).

For a fresh native run using the same integration principles, explicitly select the SOMA template (`smpl_template.type="soma"`), preserve the input BVH and explicitly arrange/discover a `motions_uniform/bvh` family and the verified shared fit at `/data/workspace/notAnyrobot/kimodo/kimodo/assets/skeletons/somaskel30/soma_base_fit_mhr_params.npz` (SHA-256 above) and compatible SOMA-X assets. Assert the resolved uniform source format and template and record asset hashes; do not accept the silent generic fallback. Generate the fitted template and moving vertices with the same topology and face ordering; verify finite outputs, joint-name mapping, source/robot frame transforms, units, FPS and exact selected frame IDs. Generate or verify SOMA face segment labels against that topology, including transfer assets and all segment coverage. Sample/train a fresh correspondence for the fitted source template and chosen G1 T-pose, bind source and robot slots to their respective meshes, reconstruct their time-varying source targets, and apply documented contact, scaling and solver settings. Record whether retaining all frames or choosing a stride and its effective FPS; stride 4 is part of the Studio example, not an intrinsic requirement. A new fitted result must be validated and inspected as a separate cohort. Existing generic-trained slots must not be treated as fitted correspondence.
